# Shared coding-agent guidance

This is the canonical root location for shared repository guidance. Some agents support the plural AGENTS.md convention, but automatic discovery depends on the tool; agents may also use nested guidance for a narrower scope. Follow the user's task, applicable higher-priority instructions and repository conventions.

## Reusable schematic tooling

- Keep general APIs, tools, tests and documentation pack-neutral in both names and behavior. An explicit pack parameter must be honored or rejected, never silently ignored. Generic helpers must not require a hidden live pack1.
- Validate pack labels and paths, respect existing no-overwrite safeguards, and protect user assets. Do not delete or replace inputs, outputs, sidecars, reports or other work merely to retry a command.
- Exercise reusable behavior with synthetic pack2/pack3 fixtures and all available packs where appropriate; ensure nested tests remain discoverable. Put genuine pack<N>-specific reference assertions, source-image notes, fixtures, regressions, reports and decisions under `test/schematic/pack<N>/`, `schematics/tooling/validation/pack<N>/`, and other appropriately scoped pack directories. Keep generic configuration out of blueprint folders.
- Preserve historical evidence, logs, paths and claims as recorded; label snapshots instead of rewriting history. Do not assume every build or pack is symmetric.
- Preserve exact Minecraft versions, DataVersions, provenance and release checks; describe unsupported cases and validation limitations honestly. Do not weaken existing repository defaults or introduce unrelated blanket restrictions.

## Schematic sources, compatibility and publication

- Treat blueprint/source JSON and its voxel and state data as the explicit source of truth. Preserve dimensions, axes, air, geometry, orientation and exact state properties. Record reference sources, unseen geometry/material assumptions and uncertainty: images can be incomplete or oblique, and image-to-build recovery is not exact. Verify outputs semantically against sources and intended version conversions; deterministic byte encoding is a separate check.
- Distinguish Java edition, exact release and DataVersion, and the actual connected server/runtime registry from schematic format revision, client/protocol versions and aliases. Prefer exact release-verified registries and data-driven, versioned block history/deltas with pinned source provenance. Do not hardcode one-off material renames, presume every new release is backward compatible, or infer semantic equivalence from identifier or state-domain changes alone. Require reviewed, version-bounded mappings and preserve properties; document loss or unknowns, require explicit consent, and fail closed on unsupported, ambiguous or invalid states. Do not claim unavailable legacy, Bedrock, feature-flag or live-placement support. Consult the current [blueprint tooling guide](schematics/tooling/BLUEPRINT_TOOLING.md) rather than freezing dataset versions or counts here.
- Compiled outputs need an explicit target-version suffix and verified version/format metadata. Select the exact release or highest eligible lower release than the safely known server release, never a physically unversioned default; an explicit compatible filename may pin a variant under the documented policy. If the server release cannot be independently determined, use documented conservative behavior and disclose its limits; unknown or no eligible versions must fail clearly. Eligibility alone does not prove placement or physics correctness. Follow the [schematic guide](schematics/README.md) and [validation provenance policy](schematics/tooling/validation/README.md), including hash-bound reports/sidecars and atomic, no-clobber publication. Preserve reviewed historical assets outside selectable roots where appropriate; never silently overwrite or discard user data.

## Symmetry and build safety

- Use symmetry as a diagnostic, not a universal requirement or proof of a flaw: inspect logical planes and meaningful local regions, reflect directional state properties and mirror-coupled door/gate geometry, and allow intentionally asymmetrical or natural structures. Before repair, explicitly justify the source side and region, state whether reference evidence supports the choice, and review exact old-to-new edits with safe thresholds; never blindly auto-fix. Distinguish authored geometry from vanilla neighbor mechanics and live updates. If blueprints change, keep counts and spot checks consistent, regenerate and validate all affected versioned artifacts and provenance, and retain historically meaningful originals. See the [symmetry guide](schematics/tooling/SYMMETRY.md) and [mechanics guide](schematics/tooling/PACK_MECHANICS.md).
- For eligible temporary hostile-mob or self-protection interruptions, preserve source identity, origin, world/dimension, options and completed work; resume only after cleanup and appropriate revalidation. Respect explicit stop, replacement, disconnect, death and world transitions; never revive cancelled actions. Avoid concurrent builder/inventory operations, coordinate creative slot writes and version-specific cleanup, avoid permanent silent hangs, and report actual failures.
- Treat gameplay-safe clearing as an objective with documented fail-closed limits, not a promise to remove every obstruction or tree. Restrict any permitted clearing to the exact intended build volume; protect unknown/unloaded blocks, block entities, valuables and player-built structures, refuse ambiguous provenance or safety, guard navigation and multi-block side effects, and verify intended-air cells. Do not claim to distinguish natural from player-placed logs or foliage when the data cannot establish it.

## Testing, scripts and reviews

- Test general behavior primarily with synthetic fixtures and, where appropriate, all available packs and versions rather than a named asset or Git history. Retain useful pack-specific historical/visual regressions in scoped subfolders. Cover semantic reproducibility separately from deterministic encoding, release ordering, suffix/missing-version decisions, cross-version palette transforms, failure paths, bounds/TOCTOU/cancellation and multi-pack portability.
- Independently validate complete affected assets and report exactly what ran. Distinguish reader/voxel agreement, registry validation, build-plan support, live-server placement and visual fidelity; never claim an unrun check or a stronger result than the evidence supports.
- Human-facing scripts in `scripts/` should have meaningful action_scope names with an extension, correct shebang and executable mode, and updated references. Preserve safety and compatibility, document and test the intended workflow and requirements, and do not blindly rename historical records.
- When the user specifically requests initial analysis and final review, create them at the requested locations and record evidence, source/credit/license limitations, accepted versus deferred items and honest gaps. Do not require review files for every task.

## Mandatory schematic E2E gate

- Quality-Gate mode must run `task quality:gate` (or `make quality-gate`) from the repository root after implementation, inspect the printed private log directory and the diff, and report each failure and blocker. The full gate runs offline checks, verifies both dependency patches, and invokes the mandatory local live schematic CI. `task quality:fast` / `make quality-fast` is an offline iteration aid only; it cannot replace the full gate. Follow [local CI prerequisites and isolated install instructions](ci/README.md); do not replace a user's ignored dependencies or lockfile. Never commit or publish unless explicitly requested.
- Whenever code related to bot actions, settings, building, schematics, or task execution is modified, you MUST run `task test:schematics` in the terminal and ensure it exits with code `0` before completing your task. If infrastructure prevents this, explicitly report the blocker and do not claim the gate passed.
