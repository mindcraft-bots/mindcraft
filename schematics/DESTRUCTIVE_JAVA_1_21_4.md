# Java 1.21.4 destructive gameplay compatibility

## Actual usable path

The existing explicitly allowlisted human request must arrive through the genuine authenticated, verified public-player-chat ingress. An online Microsoft-authenticated bot connection, server-enforced secure chat, disabled insecure coding, a fresh bot not exposed to generated code, eligible schematic provenance, and every existing volume/material/physics check remain required. Offline servers, display labels, whispers, console/LLM requests and caller-supplied trust flags do not gain authority.

The new modern digging path is **exact Java 1.21.4 / protocol 769 / DataVersion 4189**, with installed Mineflayer **4.39.0**, minecraft-protocol **1.68.0**, and the installed minecraft-data protocol schemas. This does not extend the declared support of another release, alias, plugin, proxy or modded protocol. Legacy detailed-acknowledgement handling and existing placement support are unchanged.

The bot also needs **vanilla command permission level 2** for read-only confirmation, in addition to whatever permission its existing Creative transition needs. Creative alone does not grant it. Vanilla registers the bare command names; this path does not rely on Bukkit-specific namespaced command aliases.

For each approved dig, the [private native adapter](../src/utils/schematic/authorized_gameplay_edit.js) performs these steps:

1. Before aim or any dig packet, sends a conditional test of the loaded exact target and approved starting material. A fresh unpredictable 192-bit token is returned to the bot alone by a read-only server message. No response means no dig is dispatched. Starting material is only a permission/state probe; it grants no permission beyond the existing full final-state checks.
2. At each native start/finish dispatch, repeats the existing current-world, Creative, cancellation and exact approved target checks. It assigns an operation-owned nonnegative sequence from a monotonically increasing private per-connection range starting at 1073741824, separate from the reviewed native plugins' zero/low counters. It never wraps or reuses that range. It does not patch the real client's shared writer or predict world air.
3. Consumes only an exact owned sequence acknowledgement. Vanilla may acknowledge a maximum sequence once per tick, so the latest owned value retires its dispatched prefix. Unknown, mismatched and previous-operation values cannot confirm anything. A raced finish invalidates the earlier fence/read token and must itself be fenced.
4. Observes raw server target updates, including section updates, for cache synchronization. Local events/prediction are not evidence. Each target update advances a revision and invalidates an outstanding air-read token. Packet records in one section update never become separate ordering fences.
5. After the latest owned fence, sends the read-only equivalent of “if this exact target is loaded and is Minecraft air, return this new token to this bot.” The concrete command is constructed solely from captured integer coordinates, a reviewed registry material and a private token. It uses only the vanilla loaded/block conditional and private raw-message command; it never uses a world-editing command.
6. Accepts only the exact bare token component in the raw non-actionbar server system-message packet on the same authenticated connection. The read must follow the latest air revision and latest dispatch fence, with the target still air in the observed client cache. Player/display events, feedback, decorated messages, wrong/replayed tokens, a processing acknowledgement alone, or air alone do not satisfy it. A positive read arriving before the cache update needs another read after that update.

The native promise is still not a confirmation. All confirmation listeners are removed on settlement/revocation. An unconfirmed **dispatched** edit retains the existing quarantine; reconnect/restart is required before destructive work can continue. A probe-only refusal sends no dig and does not quarantine. Cancellation and world/connection/Creative/authentication changes revoke confirmation and further edit writes. Existing bounded cleanup and world-identity-checked native cancellation remain in force. Prior confirmed edits are not rolled back.

## Why stock packets alone are not enough

The installed native digging plugin omits sequence values on start/finish and predicts air at its finish timer. In Java 1.21.4, the digging acknowledgement contains only a sequence ID, not position, state or success. Vanilla records the maximum processed action sequence and emits the fence during the connection tick. Separately, chunk broadcasting emits block or section state updates. Such an update can synchronize the cache, but carries no dig request ID and might be old queued traffic. Even a post-fence air update cannot independently prove when it was generated.

The read-only conditional therefore supplies the independent authoritative observation. Null block-entity-query NBT would not: air and ordinary non-block-entity dirt/stone can all return null. No NBT-query fallback or synthetic “successful” dig acknowledgement is used.

## Limits and fail-closed deployments

- Vanilla-style trusted server semantics and a properly authenticated server connection are deployment assumptions. A malicious server, command override, plugin or proxy can lie; the client cannot cryptographically attest server world state. This mechanism does not claim plugin compatibility or prevent concurrent edits by other actors.
- The conditional proves target air at server command evaluation, not a server transaction or exclusive causality. Newer observed target updates invalidate pending proof; existing placement revalidation still applies. No mechanism can cancel a world edit already processed by the server.
- Missing command permission, disabled/filtered messages, absent raw air updates, unrecognized component shapes, high latency, unavailable chunks or unstable updates can make a build refuse/time out. A read-back alone never repairs the local world cache. At most eight read requests are allowed per operation, including the initial probe; the existing operation timeout also applies.
- Other sequence-only releases remain unsupported for terrain digging. Historical detailed-acknowledgement adapters alone do not provide a usable authenticated public-chat route on old releases. Placement-only behavior on other admitted protocols is not a claim of usable authorized destructive ingress there.
- The deterministic fixtures and exact vanilla bytecode review establish this bounded compatibility path, not a live-server performance, universal physics or deployment certification. No live destructive test is required or claimed.
