# Schematic builds

## Quick start

The pack layout is [`screenshots/packN/`](screenshots/), [`blueprints/packN/`](blueprints/), and [`schems/packN/`](schems/), where `N` is a positive pack number. Generated binary assets belong in their pack folder; root-level legacy files are subject to the validation policy below. Use [`!listSchematics`](../src/agent/commands/queries.js:231) to see pack, numeric screenshot-folder **group**, stable **file ID**, and exact **file name** in separate fields. The primary direct selector is [`!buildSchematic("pack1:02:01")`](../src/agent/commands/actions.js:492), ordered `pack:group:fileId`; its fileId-to-fileName mapping is stored in [`schems/pack1/index.json`](schems/pack1/index.json), not inferred from filename sorting. A file ID is a stable per-group index mapping, not the file's sorted position. The term **schematic** is primary in this guide; the parser also accepts the requested aliases below.

Starting a human-routed schematic build requires the bot's exact name at the start (case-insensitive; an optional `@` is accepted), followed by `build` and one complete selector. Only a request addressed to this bot is actionable; a request addressed to a known peer is ignored by this bot. After `build`, inert descriptive text may precede the selector; `please`, `can you`, `could you`, and `would you` are allowed after the address. The selector may be followed by the placement-mode suffix described below and optional sentence punctuation; a numeric selector may also be followed by the exact phrase `instead of this unfinished building` (case-insensitive), before any mode suffix. This phrase is inert: it does not locate, remove, or replace an existing building, or choose its position. The normal nearby placement and build-safety checks still apply, and the bot reports this limitation before dispatch. Other trailing prose or instructions are rejected. Full and short labels are specifically `file id` / `id` for a stable numeric ID and `file name` / `file` for a literal basename. The typed parser returns `selectorKind: "fileId"` with `fileId` for numeric selections, or `selectorKind: "fileName"` with `fileName` for filename selections; legacy `kind`, `id`, and `filename` aliases remain for compatibility. `!listSchematics` entries expose `fileId` and `fileName` plus the legacy `id` and `filename` fields. The direct script command retains its positional `filename, x, y, z` behavior (the first argument now conceptually represents `fileName`). A literal filename named `id` or `name` should use explicit `file name id of pack1` / `file name name of pack1`, a pack/name slash form, or a supported extension; bare numbers are not filename selectors. An extension or exact selector is required when same-stem files are ambiguous. Descriptive text can contain selector-reserved words only inside balanced double quotes; only `\\` and `\"` escapes are accepted inside them. The parser does not inspect or verify the description against the selected asset, and does not guarantee arbitrary paraphrases. `colour scheme` and `database schema` remain ordinary chat unless a complete typed target shape follows. Once addressed typed selector intent is recognized, incomplete/partial, duplicate, contradictory, malformed, extra-instruction, coordinate-bearing, traversal, injection, or unresolved selectors fail closed without model inference. Messages without selector intent remain ordinary chat unless they contain recognizable addressed replacement/demolition intent as described below. Both route and direct command require configured trusted senders; `only_chat_with`, if set, must also allow that sender. Source changes require rebuilding and recreating the deployed image.

Both direct commands and typed human requests are restricted to configured `trusted_command_senders`; a non-empty `only_chat_with` list must also allow the sender. Send a direct command as `/msg Andy !buildSchematic("pack1:02:01")`. Pack names are normalized to lowercase in typed requests. Group and file ID are positive safe integers (1 through 9007199254740991), optionally written with leading zeroes, and must resolve to an existing index mapping. Prefer least-privilege game-mode permissions over `/op`; provider-specific examples are below. ### Placement configuration and overrides

Set `schematic_placement_mode` to exactly one of `delicate` (default), `raise`, `balanced`, or `destructive`. Missing or `null` settings resolve to `delicate`; a `null` command override inherits the configured setting. Other values are rejected. Set `schematic_balanced_radius` to an integer from **0 to 16** (default **4**) and `schematic_balanced_threshold` to an integer from **1 to 4097** (default **9**). The threshold is strict. Invalid configuration is rejected even with overrides; the UI exposes the same four modes.

Strategy and policy values must match the lowercase enums exactly in settings, direct commands, and human assignments. Uppercase or mixed-case values are rejected; mode, orientation, names, and human keywords and assignment keys remain case-insensitive.

Balanced search configuration also accepts `schematic_balanced_strategy` (`all`, `stepped`, or `bisect`; default `stepped`), `schematic_balanced_step` (integer 1–16; default 2), `schematic_balanced_policy` (`first_valid` or `exhaustive`; default `first_valid`), and `schematic_balanced_bisect_depth` (integer 0–3; default 2). These values are validated and frozen with each build, including resumes. The `all` strategy visits every integer offset in the radius circle; `stepped` visits offsets whose coordinates are multiples of the step. Both order candidates by squared distance, X, then Z. `bisect` visits recursively split, non-overlapping rectangles breadth-first, discards rectangles with no integer offset inside the circle, and selects the in-circle integer offset closest to each rectangle midpoint (ties by X, then Z). It deduplicates representatives, sorts each level by distance, X, then Z, and stops splitting when both rectangle spans are at most the step or the configured depth is reached; depth 0 visits only the anchor. `first_valid` stops at the first fully qualified candidate; `exhaustive` selects the lowest mismatch count among generated candidates, breaking ties by generation order, and stops after a fully qualified zero score. Pruning discards candidates that cannot win. If no candidate succeeds, a threshold-eligible candidate refused by safety inspection is reported as unsafe; otherwise the search reports no site. Sampled strategies and early selection can miss a better site. The search shares a 250,000 actual world-read and two-second limit across volume, support, and neighbor inspections; exceeding the read limit or reaching the deadline aborts instead of returning a partial result. Status reports whether the search was sampled.

Trusted addressed builds can append `using delicate mode`, `via delicate mode`, `using raise mode`, `via raise mode`, `using destructive mode`, `via destructive mode`, `using balanced mode`, or `via balanced mode` after the selector (and after the permitted inert numeric phrase, if present). Names and keywords are case-insensitive. Balanced alone accepts assignments in any order, for example `Andy build id 01 from group 02 of pack1 using balanced mode radius=6 threshold=12 strategy=bisect step=2 policy=exhaustive bisect_depth=3`. Integer assignments are unsigned. Each may occur at most once; omitted values come from settings. Other modes cannot carry balanced overrides. Malformed, duplicate, conflicting, injected, or out-of-range options fail closed.

The direct positional form is `!buildSchematic("pack1:02:01", x, y, z, "balanced", radius, threshold, "east", "stepped", step, "first_valid", bisectDepth)`. The eighth argument is an optional quoted direction or `null`; omit it for north. The four following arguments are strategy, step, policy, and bisect depth. Omit trailing arguments to use settings, or use three `null` coordinates for nearby placement, for example `!buildSchematic("pack1:02:01", null, null, null, "balanced", 6, 12)` or `!buildSchematic("pack1:02:01", null, null, null, null, null, null, "S")`. Mode, strategy and policy are quoted strings or `null`; numeric overrides are unquoted integers or `null`. Coordinates must be three finite values or all `null`. A mode overrides the configured mode; balanced overrides are valid only when the effective mode is balanced.

#### Orientation

After the complete selector (and the optional inert numeric phrase), append one direction clause, for example `facing south`, `oriented south`, `rotated south`, `rotated to south`, `rotated to face south`, `rotated towards south`, `and rotate it south`, or `then rotate to face south`. `rotate` and `rotating` are also accepted. Direction is `north`, `east`, `south`, `west`, or `n`, `e`, `s`, `w`, case-insensitively. A single mode clause and a single orientation clause may appear in either order: `Andy build id 1 from group 2 of pack1 facing east using balanced mode radius=6` or `Andy build id 1 from group 2 of pack1 via balanced mode radius=6 facing east`. Duplicate or conflicting clauses, invalid directions or extra tails are rejected, not sent to the model or silently ignored. Quoted descriptions and literal filenames are data, not orientation clauses; other prose before the selector is inert, but an unquoted recognizable direction there is rejected rather than ignored. Put the direction after the selector.

All these verbs specify **the same absolute world-cardinal rotation**, not an asset-specific front, entrance detection, or the bot's yaw. North is the identity (authored axes); east, south and west are successive clockwise quarter-turns. East and west swap the horizontal dimensions. Rotation is normalized to the transformed volume's minimum corner; explicit coordinates identify the anchor/minimum for fixed placement, while raise and balanced can relocate from their search anchor. Transforming a registry state does not guarantee the gameplay adapter can place it: non-north builds currently reject stateful targets before Creative or any edit, except verified vertical logs/wood in delicate or raise. Other normal placement, state and safety restrictions still apply. Resumes retain the original rotated plan and options.

**Implementation status:** all four modes are available within the restrictions below; none silently falls back to another.

#### Delicate default and raise mode

Delicate uses the requested fixed origin, never raises terrain, digs, clears vegetation, overwrites occupied mismatches, or adds foundation or scaffolding. Before Creative it requires every intended-air cell to be air and every non-air target to be air or already exactly match; unavailable cells fail. Correct cells are retained. Placement is limited to air, with an existing or earlier planned in-reach full-cube upward reference. It uses the reviewed passive target, foundation, entity and two-block neighbor screens described below, and the authorized native packet adapter. Unsupported sites, targets, reach, or protocol fail closed. Full-site checks are repeated after transitions and at final dispatch. Exact server confirmation and cleanup are required; earlier confirmed placements are not rolled back.

Raise uses the [site planner](../src/utils/schematic/raise_site_planner.js) under the build lease before entering Creative, then rebuilds at its selected origin. It places the planned dirt prefix first, followed by the initially-air non-air target prefix; already-correct targets are skipped. Each placement uses the leased Creative supply and authorized native adapter, requiring Mineflayer 4.39.0 and reviewed modern placement/update features. A synchronous full-site prefix check authorizes the final packet, and the exact server-confirmed state and full site are checked before advancing. No digging, non-air placement, unplanned write or pathfinding is permitted. A failure may leave confirmed partial work; raise recovery is disabled and saved raise sessions are cancelled.

The requested coordinate is an **anchor**, not necessarily the transformed volume's minimum; the offset between them is preserved. Fixed-X/Z search starts at the anchor's Y and rises at most 32 blocks, selecting the lowest accepted elevation. Already-correct occupied target cells are retained; other volume cells must be air, except reviewed terrain obstructions can cause the search to rise. Foundation candidates are air only, down to reviewed full-cube ground. The complete volume and two-block halo are inspected conservatively; nearby structures, foliage, unsupported states, missing data and intersecting entities are refused. Terrain names do not establish natural provenance. Active dimension bounds must be present in Mineflayer's dimension codec and match the game's reported minimum and height; the inclusive maximum is minimum plus height minus one. Missing or inconsistent codec data fails closed, including older protocols lacking this metadata path.

The planner's hard ceilings are a 256-cell footprint, height 64, rise 32, ground-search depth 32, 4,096 planned edits, 100,000 reads, 2,000 milliseconds per inspection, and 4,096 entities; these are not a whole-build budget. Targets must be reviewed passive states with no properties. This first execution path requires every placement to be within four blocks of the bot's assumed eye position and above a full-cube existing reference or earlier planned dirt; it does not navigate, and refuses unsupported order or reach before Creative. Multi-level structures depending on earlier volume placements are therefore not generally supported. The positive local screens do not model remote physics, plugins, unseen entities, or server behavior; a check and a server write are not atomic. Simulated integration tests are not live-server certification.

#### Human-only destructive mode

Set `allow_insecure_coding` to `false` and explicitly list the Minecraft player's canonical name in `trusted_command_senders`, such as `["Builder"]`. The **only supported destructive ingress is ordinary, verified public player chat on the authenticated connection described below**. Send `Andy build id 01 from group 02 of pack1 via destructive mode`, or the direct public-chat command `!buildSchematic("pack1:02:01", 100, 64, -20, "destructive")`. Minecraft whispers, display-only chat events, and senderless/plugin/system messages never authorize destructive mode. Nondestructive chat/whisper behavior is unchanged.

The supported connection requires Microsoft bot authentication, an observed server encryption request explicitly setting `shouldAuthenticate: true` (Java 1.20.5+), completed encrypted login with the bot's UUID/name matching its Microsoft profile, and the connected server reporting secure-chat enforcement. The server/proxy must actually enforce authenticated online player identities and secure chat for all players; these checks are not an audit of a proxy or custom server's configuration. No setting-only override, name allowlist, encryption alone, or message signature alone establishes that deployment contract. Missing handshake evidence, older protocols, offline authentication, and unavailable player mappings fail closed. Both shipped bot settings currently use offline authentication, so **neither currently permits destructive chat builds**. There is no server-operator-local approval route in this change and no proxy/browser fallback.

For each request, the gate requires the protocol's verified `playerChat` metadata, a sender UUID resolving uniquely and consistently through Mineflayer's known-player and UUID/name tables, and that canonical name matching the high-level label. Only the vanilla `minecraft:chat` type with its reviewed sender/content layout is accepted. The exact lower-level message object and unchanged body must accompany the high-level event; provenance is consumed once, never inferred from the label, and the live connection/player mapping is rechecked before execution. Destructive requests with unverified, profileless, ambiguous, unknown-type, modified, or missing provenance do not start an action or gain model/code execution privileges. The regression fixtures exercise the installed protocol signature verifier, Mineflayer chat plugin, and production build engine, including an authenticated public-chat placement and no-action/no-write refusals. Login/server identity enforcement is represented by ordinary trusted-server fixtures, not live-server authentication certification. The supported authenticated protocols still cannot authorize terrain **digging**, because the existing detailed digging-acknowledgement requirement rejects their sequence-only acknowledgements; no-op or otherwise permitted placement remains subject to all existing engine checks. This change does not broaden that engine policy.

Destructive mode is also refused while insecure code generation is enabled or after generated code has received that bot: it can retain the mutable bot and emit events. Disable coding and restart the bot before using destructive mode. The fifth direct argument selects the mode; omit it to use the configured default. An explicit balanced override remains balanced even when destructive is configured. Destructive uses the fixed nearby or direct-coordinate origin, not a balanced radius search. The normal selector, asset provenance, blocked-action and `only_chat_with` restrictions still apply. Missing, null, empty, malformed or nonmatching trusted-sender lists never authorize destructive mode, even where legacy commands otherwise accept a missing/null list. Configured or detected bot peers, internal/system messages, model-generated commands/code, and the mindserver message proxy do not supply human ingress provenance. Translated messages are eligible only if the translated text is identical to the incoming text. Public chat retains the existing multi-agent suppression rule. Missing or changed identity provenance adds a denial diagnostic without adding message content to that diagnostic; existing chat logging is unchanged.

Only registry-verified, stateless **dirt and plain stone** without attached block data can be removed as reviewed terrain mismatches, within the exact transformed schematic volume and subject to full site, entity, foundation, neighbor, physics, snapshot and final-write checks. The classifier cannot tell naturally generated terrain from player-placed dirt or stone. It does not authorize leaves, trees, arbitrary buildings, block entities, valuables, unknown/unloaded cells or unsupported target/neighbor states. Already-correct cells are preserved. A refusal or interrupted build does not automatically resume destructive work; earlier confirmed edits are not rolled back.

The reviewed native adapter requires **Mineflayer 4.39.0** and the required modern section-update and placement protocol features; other versions/capabilities fail closed. Placement requires ordered server observations of the reference and exact destination state. Legacy digging retains detailed position/status/state/success acknowledgements. **Java 1.21.4 is the only newly reviewed sequence-only digging version**: it additionally requires the authenticated online/secure-chat server connection, private non-reused outbound sequences, a matching cumulative processing fence, an actual target-air packet/cache observation, and a fresh nonce-bound read-only server conditional confirming that exact target is air. It first probes the server's starting material and read permission before sending a dig. These vanilla read-only commands need **permission level 2** (normally operator permission); Creative alone is insufficient. Missing permission/response, denied or ambiguous clearing, stale observations, cancellation, or changed identity stop the operation. An unconfirmed dispatched edit quarantines further destructive edits on that bot until reconnect/restart; confirmed earlier edits are not rolled back. Other sequence-only versions, including 1.19–1.20.x, remain unsupported for digging and refuse before Creative setup. A placement-only plan retains its existing support only when every other check and ordered confirmation succeeds. See [exact protocol/vanilla evidence, fixture coverage and limitations](DESTRUCTIVE_JAVA_1_21_4.md). No live destructive experiment was used; this is not universal server/plugin or physics certification.

Replacement and demolition are not supported. An explicitly addressed `build` request with recognizable actions or relations aimed at a structure or referent is refused with a no-replacement explanation **with or without a selector**. Examples include `Andy build replace this unfinished barn`, `Andy build replacement of the old barn id 1 from group 2 of pack2`, and `Andy build demolition of this unfinished barn id 1 from group 2 of pack2`. Verb forms (`replace`, `demolish`, `rebuild`, `remove`, `tear ... down`), noun forms (`replacement of/for`, `demolition of`), and replacement relations (`instead of`, `in place of`) are checked. Directly addressed requests beginning with recognized imperative replacement/demolition verbs are also refusal-only: for example, `Andy please demolish this unfinished barn` or `Andy replace this unfinished barn`. They never act as aliases for `build`. Noun-led discussion outside a `build` request, such as `Andy demolition of the old barn is expensive`, remains ordinary chat; noun forms are checked inside addressed `build` requests, not treated as imperative openings by themselves. Trust, known-peer addressing, and chat-allowlist restrictions still apply; malformed, multi-selector, and injected requests cannot start a build or fall through to model prompting once recognized.

This is a bounded lexical safeguard, not general natural-language understanding. It requires the exact bot address and a recognized request opening (after the supported polite prefix); unaddressed text, questions/discussion such as `Andy what does demolition of the old barn mean?`, benign descriptions such as `a demolition museum` / `a replacement parts shop`, and material alternatives such as `oak instead of birch` remain ordinary chat when they have no selector. With a valid selector, benign descriptions remain ordinary schematic builds. Full targeted replacement phrases in quoted descriptions are still refused: quotes do not waive safety. Valid selector filenames are identifiers, not instructions, even when named `replacement-of-the-old-barn` or `demolition-of-this-unfinished-barn.schem`. Filename-like tokens ending in `.schem`, `.schematic`, `.litematic`, or `.nbt` are not expanded into prose replacement instructions; that does not make those extensions selectable or grant a selector-free file build. Arbitrary paraphrases, negations, and quoted discussion inside request descriptions are not semantically interpreted; use a plain unambiguous build request to avoid conservative refusals.

Sending a bare selector after addressed `build` requests an ordinary nearby build, not a replacement. The separately accepted exact numeric trailing phrase `instead of this unfinished building` (case-insensitive, with optional terminal sentence punctuation) remains compatible: the bot warns before ordinary dispatch, does not select or remove a building, and retains all normal nearby-placement and obstruction checks. It is not accepted as a filename-selector suffix and cannot exempt replacement intent elsewhere in the request.

For explicit placement, provide all three coordinates or omit all three. Examples: [`!buildSchematic("pack1:01:01", 100, 64, -20)`](../src/agent/commands/actions.js:523) uses the supplied world position; [`!buildSchematic("pack1:01:01", null, null, null)`](../src/agent/commands/actions.js:523) uses nearby placement. In raise and balanced modes that position is the **search anchor**, not a guaranteed origin. Coordinates are direct-command-only. Send [`!stop`](../src/agent/commands/actions.js:54) to cancel a running build. Delicate and balanced builds interrupted by the hostile-mob self-preservation, cowardice, or self-defense modes may automatically resume once that mode finishes; raise and destructive builds do not automatically resume. The retry retains the original schematic bytes, resolved file, selected origin, effective options, and dimension/world; balanced never searches again. It replans from the beginning after confirming each cell in the complete schematic volume is still in its pre-build state, already matches the requested state, or, for balanced only, is air where a pre-build allowlisted foliage obstruction was cleared. Completed placements and permitted balanced clearing are therefore safe to revisit. Cleanup and mode restoration must settle successfully first. A trusted user-issued command, stop or replacement action, build failure, death, disconnect, world/dimension change, unexpected block change, unavailable block snapshot, or unfinished cleanup cancels the retry. Other interruptions are not replayed.

An early read-only inspection checks the complete transformed volume before Creative, including on resume. Delicate and destructive retain the fixed origin; raise and balanced search as described. Preflight alone never authorizes a later edit: each mode revalidates under its own guards, and changed or unloaded worlds fail closed.

For balanced clearing, the builder inspects every cell in the schematic's existing origin/dimension volume, including cells whose requested state is air. Clearing is limited to the separately reviewed stateless singleton vegetation set, and only within that volume. Leaves are deliberately refused because their removal can trigger neighboring leaf-decay updates. Vines, bamboo, sugar cane, kelp, tall plants/flowers, double-height plants, and other dependent or multi-block vegetation are refused, including when all parts appear inside the volume; the policy does not try to infer a complete physics footprint. This avoids treating companion blocks as independent cells, but a direct coordinate guard alone cannot prevent Minecraft physics side effects. Already-correct cells are preserved. Chests and other block entities, ores/valuable blocks, construction materials, logs/wood/trunks, unknown blocks, unbreakable or unreported-breakability blocks, and unavailable chunks fail preflight without clearing any cell. Logs and wood are deliberately refused: vanilla block state does not record whether they are natural trunks or player-built beams, so a reliable automatic distinction is unavailable. The same provenance limitation applies to allowlisted vegetation: player-placed flowers/crops matching the allowlist cannot be distinguished from naturally generated plants. This is type-based clearing, not proof of natural origin. World, dimension, client, entity/death, connection, build-lifecycle, interruption, and chunk/block availability are checked during clearing and immediately before builder digs/placements; identity transitions fail closed. Each candidate is re-read immediately before digging and checked for air afterward; cancellation or any failed check aborts the build. Pathfinder digging and one-block scaffolding are disabled during the build, direct builder digs are restricted to approved cells inside the volume, and the builder's broad `clearArea` operation is disabled. Final verification checks requested air cells as well as requested blocks; an unavailable or obstructed target-air cell is not success.

Placement is also fail-closed for blocks whose normal placement creates secondary cells: doors, beds, and known two-block/tall plants are rejected during schematic planning before Creative mode, inventory changes, obstruction clearing, or builder execution. Their complete orientation-dependent footprints are not currently modeled, so even a schematic containing every companion cell is unsupported. Delicate, raise, balanced and destructive apply their documented positive passive-target policies; raise is further restricted to stateless targets. Waterlogged/fluid-bearing obstruction states (including waterlogged mangrove propagules) are rejected based on their live block properties both during the complete preflight and immediately before a dig; recovery will not treat an unsafe fluid state as a safely cleared snapshot. The bot's lifecycle generation is registered when Mineflayer creates the bot and advances on protocol respawn, death, world-transition, and disconnect events. A session cannot resume after any such transition, including a respawn to a differently named world with the same dimension and retained world/entity object references.

Typed filename basenames accept only ASCII letters, digits, underscores, dots, and hyphens, with no spaces, quotes, or subdirectories; a digits-only basename needs a supported extension to be a filename selector. Filename and extension spelling must match the actual file's case exactly, even though labels and typed pack names are case-insensitive. The full `file name packN/<basename>` slash form is supported too. Direct root-relative paths have the broader confined-path behavior described in the table; these typed-chat limits do not redefine that interface.

Alias substitution also works in the full filename label: `schema name <basename> of packN` or `schema name packN/<basename>`, likewise for `schem`, `scheme`, and `schematic`. Numeric selectors retain `file offset` as well as `offset` and the bare shorthand; each may have an optional alias prefix. A `#` may precede the file ID when an alias or ID/offset label is present, and group digits may independently have a `#`. The unprefixed bare shorthand must start with digits, not `#`.

### Site-selection development status

Balanced searches generated integer horizontal offsets inside the circular radius at the anchor elevation. It counts exact transformed-cell mismatches, including intended air and empty cells where blocks are intended, and preserves matching cells. The selected candidate must pass the strict threshold and complete safety checks; selection depends on the strategy and policy above. The search is read-only, cancellable, yields, and is limited to 250,000 actual volume/foundation/surrounding-state reads and two seconds; exceeding a budget fails rather than choosing a partial result. Each candidate must pass the existing conservative clearing policy, including protection for leaves, and have registry-known, full-collision, stable natural foundation blocks beneath the entire footprint. It also requires inspectable Mineflayer entity bounding boxes with no overlap, including the bot. Unsupported, unloaded, unknown, or uninspectable data fails closed. The selected volume, foundation, and surrounding states are compared with their snapshots and occupancy is checked after the Creative transition and before guarded edits; a change aborts instead of selecting or approving a different site. These checks do not place a foundation or expand clearing.

#### Balanced target and local physics restrictions

Direct writes inside the selected volume are **not** sufficient to contain physics. A one-cell redstone-block target can power external dust and TNT; a sponge can absorb water beyond its cell, and a piston can move external blocks. Balanced therefore additionally requires **every target**, even an already-matching cell, to belong to a positive reviewed passive-state set in [`balanced_physics_policy.js`](../src/utils/schematic/balanced_physics_policy.js). It does not use a hazard-name denylist or assume that a placeable item is safe. Ordinary full-block stone/brick variants, dirt-like terrain, reviewed wood planks/logs, glass, wool, concrete (not powder), terracotta, and air are supported when the live registry contains them with the complete expected property schema. Axis and snowy values must be valid; absent, additional, fluid-bearing, or otherwise unsupported properties refuse the target. Machinery, power sources, explosives, sponges, falling blocks, plants, fluids, partial shapes and unreviewed blocks are not supported as balanced targets. Delicate and destructive also use this passive-target screen; raise adds further restrictions. No mode falls back to legacy placement.

Actual states **inside** the volume are also positively classified, including already-matching cells and intended-air obstructions. They must be in the passive set or the separate reviewed stateless singleton clearing set (short grass, fern, dead bush and the explicitly enumerated small flowers), without attached data. Balanced does not permit the broader historic allowance for saplings, fungi, mushrooms, crops or other unreviewed vegetation. This does not establish natural provenance: a player-placed flower is indistinguishable from a natural one. Construction materials are preserved only when already correct, not authorized for demolition by the passive classification. Every guarded edit reclassifies actual volume states as well as surrounding states; after an edit only that edited cell's inspectable, supported snapshot may advance.

Balanced also reads the surrounding two-cell box on **all sides**, including above and below, without editing it. Every exterior cell must be loaded, inspectable, free of attached/block-entity data, and in that same positive passive-state set. This screens local redstone/conductor, observer, piston/quasi-connectivity, fluid, falling-block, attachment and similar update-sensitive neighbors, including diagonal/two-step arrangements; even an apparently idle or unpowered machine is refused. A distant circuit does not become acceptable merely because its TNT endpoint lies beyond the box: its local active interface is disallowed too. Surrounding states are snapshotted, reclassified and compared after transitions and immediately before each guarded dig/place. The builder advances only its own edited-cell snapshot, never silently approving exterior changes. Resume inspects the frozen origin under the same policy before another Creative transition. Initially unsafe targets/sites refuse **before Creative, inventory supply or any world writes**; changes detected after a transition refuse further world writes and retain normal cleanup/restoration behavior. Refusal diagnostics identify unsupported targets or a representative unsafe candidate/neighbor, rather than treating a low mismatch count as permission.

**Limits:** this is a conservative local admission rule, not a physics sandbox or proof of universal isolation. The two-cell screen is not a maximum propagation-distance claim; the positive target restriction is essential, and an empty surrounding box never authorizes an active target. No arbitrary physics graph, remote light/growth/scheduled-tick effects, ongoing world activity, malicious/custom server behavior, or plugins/datapacks are simulated or contained. Revalidation occurs before Creative, after asynchronous setup, and at the guarded dig/place API boundary after navigation and builder waits; it is not a server transaction or a protocol-packet firewall. Mineflayer's own asynchronous internals and server updates can still race client inspection and packet application. The checks rely on the connected registry and client-visible loaded block/entity data; they cannot establish absence of undisclosed server-side data or cancel effects already triggered by an earlier packet. Do not interpret an accepted build as a guarantee that nothing outside the footprint can ever change. Automated tests exercise the actual balanced mode/adapter/guard pipeline with deterministic world fixtures and hazard oracles; they are not a live-server physics certification. No destructive live demo is required for these regressions.

## Game-mode permissions

A schematic build needs the bot to enter Creative mode, then attempts to restore its previous mode. On permission-managed servers, prefer granting only the relevant game-mode permissions rather than using `/op`. The command that handles `/gamemode` determines which permission nodes apply: vanilla/Paper/Bukkit and EssentialsX can use different providers, and EssentialsX may override the command. Grant the family that applies on your server; do not assume both are required. Per-mode vanilla nodes can also vary by platform, so test an actual Creative-to-Survival switch.

From the server console, replace `<BotName>` with the bot's exact Minecraft name and grant the vanilla/Paper/Bukkit nodes that your server supports:

```text
lp user <BotName> permission set minecraft.command.gamemode true
lp user <BotName> permission set minecraft.command.gamemode.creative true
lp user <BotName> permission set minecraft.command.gamemode.survival true
```

If EssentialsX handles `/gamemode`, use its applicable nodes instead:

```text
lp user <BotName> permission set essentials.gamemode true
lp user <BotName> permission set essentials.gamemode.creative true
lp user <BotName> permission set essentials.gamemode.survival true
```

These are console commands without a leading slash. In-game `/lp` commands require administrator permission. To inspect the bot's explicit LuckPerms user permissions, run:

```text
lp user <BotName> permission info
```

That output may not show every effective permission inherited from groups or context; if needed, verify the provider configuration or use LuckPerms verbose while testing. The bot sends unqualified `/gamemode creative` and `/gamemode <previous mode>` commands, so confirm that the selected provider permits both transitions. If the bot starts in Adventure or Spectator and must return to that mode, grant the corresponding mode permission as required by your provider; otherwise keep its initial mode Survival or Creative.

Operator status is a broad fallback, not a requirement or preferred solution on permission-managed servers. Permissions may still be constrained by server game-mode settings or other plugins. If a mode change is denied, the build should fail safely; Creative inventory updates and their cleanup/restoration are best effort if the server rejects them. Review the placement and final result in-world.

## Safe code updates and Docker redeployment

Use Git to transfer reviewed commits between clones. Commit the intended code/assets, review the exact commit, push the exact tracked branch to the intended repository or fork, and configure the destination checkout to track that intended remote branch. The updater derives the remote and branch from that checkout's configured upstream; it does not assume `origin`, `main`, or `develop`, switch branches, or push changes.

### First-time bootstrap and destination review

The update script is itself part of the code being transferred, so it is not present in a pre-existing destination clone until that clone has received the commit containing it. Bootstrap the script through the destination's normal reviewed Git procedure, not by assuming it can update itself. First back up and manually reconcile the destination's tracked, untracked, and ignored data, confirm the intended remote/branch, and review all host-specific configuration. An earlier destination inspection reported 16 modified tracked paths and 343 untracked paths, including conflicts such as a differing schematic index; those are historical counts, not a current safety check. Do not run an update there until local changes are backed up and reconciled. Inspect ignored runtime data separately as well. No updater can infer which local configuration or runtime state should win, and this audit does not inspect or modify that deployment checkout.

Tracked schematic assets (indexes, binaries, blueprints, screenshots), source, and tests transfer through Git commits. Confirm intended files are tracked with `git ls-files`. If Git LFS or submodules are introduced, verify their objects/checkout explicitly; the updater refuses submodules and Git LFS pointer files rather than claiming to hydrate them. Ignored files do not transfer. Provision `keys.json` and other secrets securely; do not commit or copy credentials as part of a blanket repository migration. Histories/state and dependencies likewise require deliberate destination-side handling.

### Update, build, recreate, verify

From the repository root, only after reviewing and backing up the destination:

```sh
scripts/update_project.sh --apply \
&& docker compose build bot-andy bot-alice \
&& docker compose up -d --force-recreate bot-andy bot-alice
```

The `&&` chain stops before Docker if update is blocked or fails. Then check status and inspect recent startup logs locally:

A missing cached ref blocks this check; `--apply` can fetch the configured branch to create that ref. `--apply` fetches without force and only fast-forwards a clean, non-bare, named, non-shallow, non-sparse, non-partial checkout with no Git operation in progress, unsafe index flags, submodules, configured checkout filters, or untracked files. Fetch disables tag updates, pruning, submodule recursion, automatic maintenance, commit-graph writes, and opportunistic configured ref mappings; it may still write fetched objects, the selected tracking ref, reflogs, and FETCH_HEAD even if a later safety check fails.

The default target is the checkout containing the script, not the caller's directory; `--repo PATH` selects an explicit checkout (or a directory inside it). Symlinked parent directories and linked worktrees are supported, but symlinked script files are not resolved to their referent. Checkout/script/metadata directory paths containing newlines are unsupported and refused; filenames inside a supported checkout may contain spaces, tabs, or newlines.

Git's `merge --ff-only --no-overwrite-ignore` protection is retained. Adversarial tests verify ignored file/directory/symlink collisions, including an ignored parent directory containing tracked and ignored children, fail without changing HEAD, index bytes, user bytes, or symlinks on the tested Git. Unrelated ignored runtime data remains in place on successful updates. These are not general atomicity guarantees: I/O errors, disk exhaustion, process termination, or unrelated concurrent writers can leave partial checkout changes. There is no automatic rollback, which could itself destroy user changes. After any failure, inspect HEAD, index, and files and preserve data before retrying; never assume failure means nothing changed. The advisory directory lock excludes concurrent calls in the same worktree only, not unrelated Git/file writers or other linked worktrees sharing refs. Traps remove an owned empty lock on normal exit and handled HUP/INT/TERM; a kill/crash or signal during lock acquisition can leave a stale lock.
